**Customer Risk Monitoring ETL Pipeline (SQL)**

**Overview** 
This project demonstrates the design and implementation of an end-to-end ETL pipeline for a fintech risk monitoring use case. The objective of this project is to transform messy operational data into an analytics-ready customer risk feature mart that can support fraud monitoring and behavioral analysis.

Raw dataset contained several common data quality issues such as:
- Missing identifiers
- Invalid timestamps
- Inconsistent text formatting
- Improperly formatted numeric values
The pipeline cleans, validates, and transforms this data into structured tables suitable for downstream analytics and risk monitoring.

**Business Problem**
Fintech platforms rely on transaction and fraud data to monitor customer risk and detect suspicious behavior.

However, raw operational data often contains inconsistencies that make direct analysis unreliable.

The goal of this project was to build a robust SQL-based ETL pipeline that:
- Ingest raw data 
- Creates staging tables to avoid messing with original data.
- Performs data quality profiling 
- Standardizes and validates records
- Isolates unusables records
- Produces a customer-level risk feature mart
This enables analysts and risk teams to monitor transaction behavior and fraud exposure at the customer level.

**ETL Pipeline Architecture**
The pipeline follows a layered data architecture designed to preserve raw data integrity and ensure transformations do not alter the original source data.
The workflow seperates the pipeline into distinct layers:
Raw CSV Files
      ↓
Raw Tables (Imported Data)
      ↓
Staging Tables
      ↓
Data Quality Profiling
      ↓
Cleaning & Standardization
      ↓
Analytics Transaction Base
      ↓
Customer Risk Feature Mart

This approach ensures that the original imported data remains unchanged and available for auditing and reprocessing if needed.

**ETL Steps**
1. Raw Data Import
The raw data was imported into raw data tables. These tables store the original data exactly as received.
Raw tables created:
    - customers
    - transactions
    -fraud_flags
These tables act as source layer and remain untouched throughout the pipeline.

2. Staging Layer
To prevent accidental modification of original data, the staging layer is created.
Data from the raw tables was copied into the staging tables where transformations and profiling could safely be performed.
Staging tables:
    - customers_staging
    - transactions_staging
    - fraud_flags_staging
The staging layer serves several purposes:
    - protects raw data from modification
    - provides workspace for transformations
    - allows data profiling before cleaning 
    - supports reproducible ETL workflows

3. Data Quality Profiling
Before cleaning the data, SQL profiling queries were used to identify data quality issues such as:
- missing identifiers
- placeholder values (null, missing, n/a)
- invalid timestamps
- inconsistent text formatting
- duplicate identifiers

Key findings:

Transactions:
- 1090 rows missing customer_id
- 885 invalid timestamps

Customers:
- 169 invalid or missing age values
These issues were addressed in the cleaning layer.

4. Data Cleaning & Standardization 
Cleaning rules were applied to produce validated datasets.

Customers
- trimmed whitespace
- standardized text casing
- validated age values (invalid values set to NULL)

Transactions
- parsed timestamps into valid datetime format
- removed currency symbols and commas from amount values
- standardized categorical variables
- filtered unusable transaction records

5. Fraud Data Integration
Fraud flag data was integrated into the transaction dataset to produce risk-aware transaction base.

6. Feature Engineering
Customer-level behavioral features were generated to support risk monitoring.

Examples include:
- total transactions

- average transaction amount
- fraud transaction count
- fraud rate

- channel usage distribution 

These features were stored in the final table:
    - customer_risk_feature

**Data Quality Framework**

Ensuring data reliability was a key objective of this project. Before transforming the data, a structured data quality framework was applied to detect and address inconsistencies in the raw datasets.

The framework focused on four primary categories of data quality checks.

1. Missing Value Checks

Missing values were identified across all datasets to determine whether records were usable for analysis.

Example SQL profiling logic:

SELECT
    SUM(customer_id IS NULL OR TRIM(customer_id)='') AS missing_customer_id,
    SUM(timestamp IS NULL OR TRIM(timestamp)='') AS missing_timestamp
FROM transactions_staging;

Key findings:

| Column                   | Missing Values |
| ------------------------ | -------------- |
| transactions.customer_id | 1,090          |
| transactions.timestamp   | 210            |
| customers.age            | 80             |


These issues required validation rules before further transformation.

2. Invalid Format Detection

Certain fields contained values that did not match the expected format.

Examples included:

timestamps such as 2025-13-40 25:61:61

currency-formatted numeric values like R1,234.56

inconsistent casing in categorical variables

Validation logic was applied to identify valid timestamps and numeric values before conversion.

Example validation rule:

CASE
WHEN timestamp REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}'
THEN STR_TO_DATE(timestamp,'%Y-%m-%d %H:%i:%s')
ELSE NULL
END
3. Duplicate Record Detection

Duplicate identifiers can lead to incorrect aggregations and misleading analytics results.

Window functions were used to detect potential duplicates.

Example query:

WITH duplicates AS (
SELECT
    *,
    ROW_NUMBER() OVER(PARTITION BY transaction_id) AS row_num
FROM transactions_staging
)
SELECT *
FROM duplicates
WHERE row_num > 1;

No duplicate transaction identifiers were found in this dataset.

4. Validation Rules

After profiling, validation rules were applied to ensure only reliable records were included in the analytics layer.

Examples:

| Rule                    | Action                         |
| ----------------------- | ------------------------------ |
| Missing `customer_id`   | Exclude from analytics dataset |
| Invalid timestamp       | Convert to NULL                |
| Invalid amount format   | Convert to NULL                |
| Age outside valid range | Set to NULL                    |


Transactions failing critical rules were excluded from the analytics layer.
